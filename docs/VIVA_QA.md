# Viva Questions & Answers

Likely examiner questions for this project, with defensible answers grounded in the actual code and results. Weighted toward the CT-264 classification study (the graded CCA), with a section on the agent and one on the "hard" questions.

> Real numbers used below: **420 rows** (20 real + 400 synthetic), **9 categories**, imbalance ratio **≈ 3.6**, mean length **35.6 words**, split **336 train / 84 test**, test F1-macro **1.000**, 5-fold CV F1-macro **LR 0.990 / NB 0.993 / SVM 0.990**, tuned best **C=0.5, max_features=3000, unigrams (CV 0.991)**, ensemble **1.000**.

---

## A. Problem & data

**Q1. What problem does your project solve?**
A university helpdesk gets many student emails. We classify each email's **category** (one of 9) from its text, so it can be routed to the right office automatically and urgent/sensitive cases reach a human fast. It's a supervised **multi-class text-classification** problem.

**Q2. What are the inputs and outputs?**
Input = email `text` (subject + body). Output = `category` ∈ {fee, hostel, academic, technical, wellbeing, harassment, legal_media, security, other}.

**Q3. You were asked for at least two datasets. What are yours?**
(1) **20 real emails** from the project inbox, labelled from the agent's `outbox.json`. (2) **400 synthetic emails** generated by `analysis/generate_data.py` across all 9 categories with realistic Pakistani-university context. Merged → **420 rows**.

**Q4. Why synthetic data — isn't real data better?**
20 real emails are far too few to train and cross-validate a 9-class model, and real student emails are private. The synthetic set gives volume and balance; the real set keeps us anchored to genuine, messy text. We're explicit that synthetic data is the main limitation (see Q18).

**Q5. Where did the labels come from?**
Real emails: the category the LLM agent assigned (`outbox.json`). Synthetic emails: the generator knows each email's category because it builds it from that category's template, so the label is correct by construction.

## B. EDA & class imbalance

**Q6. What did your EDA show?**
Categories range from `academic` (76) to `security`/`legal_media` (21 each); priority skews `high` (202) because sensitive categories are always urgent; emails are short (mean 35.6 words); and each category has a clear, distinct vocabulary (top-words chart). Short, vocabulary-separable text is exactly why TF-IDF + a linear model is the right choice.

**Q7. Is there class imbalance, and how did you measure it?**
Yes — moderate. **Imbalance ratio = largest class / smallest = 76 / 21 ≈ 3.6**. Shown in `class_imbalance.png`.

**Q8. How did you address the imbalance?**
Three ways: (1) `class_weight='balanced'` on Logistic Regression and Linear SVM, which up-weights rarer classes in the loss; (2) **F1-macro** as the primary metric, which averages all classes equally so big classes can't hide poor minority performance; (3) **stratified** splitting and cross-validation, so every class appears in every split. Naive Bayes has no class-weight parameter, so its `alpha=0.1` smoothing plays the protective role.

**Q9. Why F1-macro and not accuracy?**
Accuracy can look great while ignoring a small class entirely. F1-macro weights each of the 9 classes equally, so it punishes neglecting `security` or `legal_media`. With imbalance, macro-F1 is the honest headline number.

## C. Preprocessing & features

**Q10. What preprocessing did you do?**
Combine subject+body; lowercase; strip punctuation; drop 1-character tokens; then TF-IDF vectorise. Missing subject/body default to empty strings so no row is dropped and every email still gets a prediction.

**Q11. Explain TF-IDF simply.**
**TF** = how often a word appears in this email; **IDF** = how rare the word is across all emails. TF×IDF is high only when a word is frequent *here* and rare *overall* — i.e. genuinely informative. "the/please" score low; "voucher/harassment/wifi" score high.

**Q12. What TF-IDF settings and why?**
`max_features=5000` (cap size, drop ultra-rare noise), `ngram_range=(1,2)` (single words **and** pairs like "late fee", "self harm"), `sublinear_tf=True` (log-dampen repeated words so a 10× mention doesn't dominate — Naive Bayes keeps this off because it expects raw counts).

**Q13. What is an n-gram?**
A unigram is one word; a bigram is a word pair. Bigrams capture meaning that single words miss ("self harm" vs "self" + "harm").

**Q14. Why is the vectoriser inside a Pipeline?**
To prevent **data leakage**. In a `Pipeline`, TF-IDF learns its vocabulary from the *training* fold only; the test fold is transformed with that vocabulary but never shapes it. Vectorising the whole dataset first would let the model peek at test data and inflate scores.

## D. Models & training

**Q15. Which models and why these three?**
**Logistic Regression** (strong, interpretable linear baseline for sparse text), **Multinomial Naive Bayes** (classic fast text baseline), **Linear SVM** (often best on high-dimensional TF-IDF). All are appropriate for "moderate complexity": a few hundred short emails. Deep models would overfit this volume and add no value.

**Q16. How does training actually work in your code?**
`pipeline.fit(X_train, y_train)` — one line. It (1) fits TF-IDF on the 336 training emails, then (2) adjusts the classifier's internal weights until its predictions on those emails best match the true categories. `pipeline.predict(X_test)` then runs a new email through the same steps.

**Q17. How does Logistic Regression classify text, in words?**
It learns a weight per word per category. For a new email it sums the weights of the words present and picks the category with the highest score (converted to a probability). Those weights are what the feature-importance chart shows.

## E. Evaluation (incl. the hard question)

**Q18. Your models score 100% — isn't that suspicious?**
Yes, and we flag it honestly. 100% test accuracy means the task is *too easy for this data*: the 400 synthetic emails are template-generated, so each category has an almost give-away vocabulary that any linear model separates trivially. The number to trust is the **cross-validation (~0.99)**, and even that would drop on genuinely messy real emails. Documented in `docs/TECHNICAL_REPORT.md` §9. The feature-importance chart confirms the models learned *sensible* words, not artefacts — so it's "easy data", not "broken evaluation".

**Q19. What is cross-validation and why use it on top of a test split?**
A single split can be lucky. **5-fold stratified CV** splits data into 5 parts, trains on 4 / tests on 1, five times, and averages. It's a more robust estimate. Ours: LR 0.990, NB 0.993, SVM 0.990 — effectively tied.

**Q20. What does the confusion matrix tell you?**
Which categories get mistaken for which. Ours is a clean diagonal (predicted = actual almost everywhere), consistent with the near-perfect scores.

**Q21. Precision vs recall?**
Precision = "when the model says *fee*, how often is it right?" Recall = "of all real *fee* emails, how many did it catch?" F1 is their harmonic mean; F1-macro averages F1 over all 9 classes.

## F. Performance improvement

**Q22. What did you do to improve performance (the rubric asks for this)?**
Two things on the best model (Logistic Regression): (1) **hyperparameter tuning** with 5-fold `GridSearchCV` over TF-IDF (`ngram_range`, `max_features`) and the classifier's `C`; (2) a **hard-voting ensemble** of all three models.

**Q23. What did tuning find?**
Best = `C=0.5, max_features=3000, ngram_range=(1,1)` at CV F1-macro 0.991. The lesson: a *simpler* model (single words, fewer features, stronger regularisation) generalises just as well — the right outcome on a small dataset, because simpler = less overfitting.

**Q24. What is `C`?**
The inverse regularisation strength in Logistic Regression / SVM. High `C` = fit the training data hard (overfit risk); low `C` = keep the model simple. The grid chose a low `C` (0.5) — "keep it simple".

**Q25. What is an ensemble and did it help?**
Run several models and combine them — here `voting='hard'` takes the majority predicted label. It got 1.000; since everything was already near-perfect it matched rather than beat the single models. Ensembles usually help by averaging out individual mistakes.

## G. The agent & how the ML relates

**Q26. Is the trained model used by the live app?**
No — honestly, no. The running product (email → triage → reply draft) uses the **Gemini LLM agent** (LangGraph). Nothing in `app/`, `backend/`, or `frontend/` calls the scikit-learn models. The classifier is a **standalone study** that (a) satisfies the CT-264 rubric and (b) serves as a measured baseline.

**Q27. Then why build the classifier at all?**
Two reasons: the course requires a trained-and-evaluated *classifier* (an LLM alone doesn't satisfy that), and it's an honest **comparison** that justifies the product's design choice — it shows *why* we use an LLM for the real work.

**Q28. Classifier vs LLM agent — the trade-off?**
Classifier: predicts category only; needs labelled data; free, offline, millisecond, auditable. LLM agent: category + priority + escalation + policy lookup + writes the reply + safety net; zero-shot from instructions; costs API time. They're complements: a classifier is an ideal cheap first-pass router; the LLM does the judgement-heavy work.

**Q29. Could you integrate the classifier into the product?**
Yes, as future work: use it as a fast offline router to pick the category in milliseconds and only call the expensive LLM for the reply and escalation. It's not integrated today, and we don't claim it is.

**Q30. What does the agent do that a classifier can't?**
Draft a policy-grounded reply under 150 words, decide *who* to escalate to and *why* (citing ESC rules), look up the right policy clause, and run a life-safety net that forces escalation on hazard/self-harm wording. That's generation + reasoning + safety, not classification.

## H. Ethics, robustness, limitations

**Q31. Any ethical/privacy considerations?**
Yes: real student emails are sensitive, so the dataset is mostly synthetic and no personal data is published; the agent treats email text as untrusted (prompt-injection defence) and never sends anything (drafts only); sensitive categories (harassment, wellbeing) route to humans, never auto-resolved.

**Q32. Main limitations of the ML part?**
Synthetic data is template-based so scores are optimistic; only 20 real emails so we can't measure the real-vs-synthetic gap per class; TF-IDF is bag-of-words (ignores word order/meaning); Roman Urdu is treated as plain tokens.

**Q33. What would you do differently / next?**
Collect more real labelled emails; add harder, ambiguous synthetic cases; hold out *by source* (train on synthetic, test on real) to measure the true generalisation gap; try a transformer embedding if the real corpus grows.

**Q34. How is this reproducible?**
`random_state=42` everywhere (split, models, CV, grid). `pip install -r analysis/requirements.txt`, open `analysis/eda.ipynb`, Restart & Run All — all 11 charts regenerate in `analysis/plots/`.

## I. Quick code-level questions

**Q35. Why `stratify=y_cat` in the split?** So each category keeps its proportion in train and test — critical with imbalance so small classes aren't missing from the test set.

**Q36. Why `max_iter=1000` / `2000`?** So the optimiser has enough iterations to converge on the sparse TF-IDF features and doesn't warn/stop early.

**Q37. Why does Naive Bayes use `sublinear_tf=False` when the others use `True`?** Multinomial NB models raw term counts; log-scaling them breaks that assumption, so it keeps raw TF while LR/SVM benefit from the dampening.

**Q38. Why `alpha=0.1` in Naive Bayes?** Laplace/Lidstone smoothing — stops a word unseen in a category from forcing its probability to zero; 0.1 is light smoothing that worked best here.

**Q39. How many features does the model actually use?** Up to 5000 TF-IDF terms (unigrams+bigrams) in the baseline; tuning preferred 3000 unigrams.

**Q40. One-line summary of the whole study?** "We framed helpdesk-email routing as 9-class text classification, built a 420-row two-source dataset, handled a 3.6× imbalance, trained three TF-IDF classifiers to ~0.99 cross-validated F1-macro, improved with tuning and an ensemble, and honestly explained that the perfect test scores reflect easy synthetic data."
