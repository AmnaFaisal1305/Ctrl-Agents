System architecture

An autonomous agent reads student emails, looks up the university policy, decides category, priority and escalation, and drafts a policy-grounded reply. Nothing is ever sent. This page draws how the parts fit and how one email flows through them. ARCHITECTURE.md stays the written source of truth.

05

Fixed code and agent decisions

The rule: the model decides, code only validates and falls back. Nothing is keyed to an email id, subject or sample text.

Fixed code (deterministic)

  • Find and read files, tolerate bad JSON, normalize text
  • Parse the policy into clauses and serve LookupPolicy
  • Validate: schema, word limit, sign-off, codes exist and were looked up, no invented contacts
  • Retry with backoff, timeout, turn budget
  • Fallback row when anything fails
  • Life-safety net for ESC-1 and ESC-3

Agent decides (LLM)

  • Category (open set: fee, hostel, academic, technical, wellbeing, harassment, legal_media, security, other)
  • Which policy to look up, and how many times
  • Priority, whether to escalate, and to whom
  • Reply text, tone and language (English or Roman Urdu)
  • Confidence and agent_notes
06

Guards around the model

The model is never trusted to be right. Three layers check it, and the email text is always treated as data.

Hard validators

A hard issue is fed back to the model.

  • Schema valid, priority in the set, confidence in [0, 1]
  • Reply under 150 words, ends with Student Helpdesk
  • Every policy code exists, non-ESC codes were looked up, one appears in the reply
  • Escalated: reason names an ESC code and policy_refs is not empty
  • No phone, email or URL that is not in the policy or the student's email
  • No markdown, no copy of the incoming email

Soft validators

Logged, and they cap confidence.

  • Greeting uses the student's first name
  • agent_notes is 1 to 400 characters
  • Reply language matches the email

Safety and injection

Other rules stay with the agent to avoid false positives.

  • Pre-flags (hazard, wellbeing, injection) are hints, never decisions
  • Email sits inside <email> tags and is never obeyed
  • Post-check forces escalate for ESC-1 and ESC-3 only, and logs decided_by: rule
  • Suspicious mail goes to ESC-6, IT Security
Fallback triggers. Bad or empty file · no usable text · LLM down after retries · 6-turn budget used · 2 failed submits. The row escalates, has confidence 0.0 and a safe holding reply.

Backend and live streaming

The FastAPI app runs the agent in-process on a background thread. The UI never polls: it follows the same JSONL step log the CLI writes.

MethodPathPurpose
GET/api/healthliveness, always open

DELETE/api/emails/{id}delete, web-* emails only

GET/api/outboxthe current outbox.json
GET/api/runstatus of the current or last run
GET/api/statscounts for the dashboard
GET/api/policyparsed policy clauses

With API_KEY set, every route except health needs X-API-Key. SSE accepts ?api_key= because EventSource cannot set headers. The key ships in the UI bundle, so it only guards casual access on localhost.

10

Design principles

Fail soft

  • Every email gets a row, whatever breaks
  • Errors are logged, then the run continues
  • Output file is written atomically

Untrusted input

  • Email text is data, never instructions
  • Injection is flagged and escalated, not obeyed
  • No invented contacts, amounts or deadlines

Model decides, code checks

  • No hardcoded replies or id-keyed rules
  • Validators enforce grounding in the policy
  • Forced decisions are rare and logged as rules

Observable

  • One log line per step with the reason
  • Console, JSONL and the UI show the same trace
  • LLM call count printed after each run

Quota aware

  • Temperature 0, 6-turn cap, 2 workers
  • 429 means retry with backoff, and say so
  • --only-new skips unchanged files

Never send

  • Gmail scopes: readonly and compose only
  • A test greps the code for send calls
  • No other messaging path exists
